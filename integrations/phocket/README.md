# Grocious multiuser collector

An AGPL-3.0 fork of Grocious's Coop, Rema and Trumf collection modules, maintained as a separate
service from Phocket. See NOTICE and LICENSE. Complete corresponding source is
served at `/source`; Phocket exposes that download to its users.

Build the upstream `grocery-login:latest` image first (Grocious `login/Dockerfile`),
then build this Dockerfile. It adds Flask, cryptography, Gunicorn and Poppler.
Run one Gunicorn worker with threaded requests; the coordinator owns in-memory
login challenges. Python Playwright/Chromium 1.47 comes from that base image.

Set `GROCIOUS_DATA=/data` and `GROCIOUS_SERVICE_KEY_FILE=/run/secrets/grocious-key`.
Mount a private writable data directory, the key read-only, and tmpfs at `/tmp`.
Run as UID 1001/GID 100. No host port or Docker socket is needed. Only Phocket's
web and scheduler services should reach port 3015 on the Docker network.

Profiles are opaque 64-character lowercase SHA-256 identifiers generated by
Phocket from its user ID and the service key. Every profile request needs
`Authorization: Bearer HMAC-SHA256(key, "profile:" + profile)`. Neither profile ID
nor bearer tokens are accepted from the browser. A token for profile A cannot
access profile B, including when receipt IDs happen to be identical.

API (under `/v1/profiles/<profile>/`):

- `GET status`: connection, current login attempt and collection status.
- `POST login`: JSON `username`, `password`; returns an attempt ID immediately.
- `POST reserve`: internal JSON `account_hash`; reserves an existing Phocket account
  binding before a legacy user logs in. It neither logs in nor copies credentials.
- `POST sms`: JSON `attempt`, `code`; six digits, at most three submissions.
- `POST cancel`: cancel the pending login without changing archived receipts.
- `POST logout`: remove login tokens; keep archived receipts and account binding.
- `POST sync`: enqueue a collection if one is not already running.
- `GET api/archive/coop`: receipt manifest using the existing Grocious protocol.
- `GET archive/coop/<id>.json`, `GET archive/coop/<id>/file/<filename>`: originals.

Login uses a fresh browser context and OAuth PKCE/state validation. The browser
does not save sessions or screenshots. Credentials and SMS codes are not written
to disk or logs. Restarting the service expires unfinished challenges. Sessions
are stored in profile-specific Fernet vaults; rotated tokens are checkpointed
before collection. Plain tokens are materialized only in private tmpfs job
directories and removed at job completion. Archive collection runs in separate
processes with a profile-specific data directory; no environment variables are
changed in the shared HTTP process. The same Coop account cannot bind to two
profiles, and an existing profile cannot silently switch accounts.

Initial collection retrieves the available history; later collection checks the
current and previous month every 15 minutes. Failed collection is retried, while
source failures and failed login are visible in Phocket. SMS and login challenges
expire after seven minutes; up to two logins can run concurrently, with four
starts per profile per ten minutes. A real Coop account is needed for final live
login verification; tests use synthetic accounts and simulated OAuth/SMS flows.

Run tests with `PYTHONPATH=app python -m unittest discover -s tests`.


## Three personal connections

Use `/v1/profiles/<profile>/providers/<provider>/` with `provider` equal to
`trumf`, `rema` or `coop`. All status/login/SMS/cancel/logout/reserve/sync and
archive endpoints have this prefix. Existing unprefixed URLs still select Coop.
The profile ID and HMAC are derived exclusively by the authenticated Phocket
server; browser input must never choose a profile or user ID. Apply Phocket
membership permissions and CSRF validation to every browser action.

Rema requires a Norwegian mobile number and SMS code (`password` is an empty
string). It uses OAuth PKCE with callback state validation and stores rotating
tokens. Trumf requires a mobile number, password and any requested SMS code; its
NextAuth cookies and account access token are stored in the encrypted vault.
Coop retains its existing PKCE login. Each attempt has a fresh Chromium context;
passwords and SMS codes exist only in memory. Account identity comes from the
provider-issued access token's subject; do not accept identity from form data.

Coop keeps the existing `/data/profiles` and SQLite layout. New Rema and Trumf
collectors live under `/data/providers/<provider>` with independent attempts,
queues, account bindings and archives. Encryption keys include user and provider;
Coop's existing encryption remains readable. Disconnecting one provider leaves
other connections and archived receipts intact. Each provider permits at most
two concurrent logins, four starts per user per ten minutes, and three SMS tries.

Archive paths include the selected provider, for example
`providers/rema/api/archive/rema` and `providers/trumf/archive/trumf/<id>.json`.
A provider cannot request another provider's archive. Coop originals include PDF;
Rema/Trumf preserve original JSON receipt data and available supplier documents.
Initial collection backfills available history; later collection runs every
15 minutes. Rema token rotations and refreshed Trumf sessions are checkpointed
before fetching receipts, guarded against a changed account identity.

Phocket's adapter needs independent receipt sources and pending login records
keyed by `(workspace_id, user_id, provider)`. Preserve existing source/receipt IDs
when migrating the old Coop-only database. Bind existing account hashes before
renewing login and validate the source provider, fingerprint and document hashes
before committing receipt data. Do not store passwords in Phocket's database.

Automated tests exercise all three login flows in real Chromium against
simulated supplier pages, invalid OAuth state, cross-user/provider SMS and vault
isolation, cancellation, refresh checkpoints and archive ownership. Real provider
credentials and SMS are still needed for final live verification.
